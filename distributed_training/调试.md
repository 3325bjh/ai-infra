# 调试 PyTorch 分布式应用

分布式训练常见问题包括：某个 rank 没有进入通信、不同 rank 调用了不一致的集合通信、张量形状不匹配、NCCL 选错网卡，以及 DDP 存在未使用参数。本页整理 PyTorch 的常用排查工具。

## 1. 启动时开启调试日志

先在启动训练前配置环境变量：

```bash
# Linux
export TORCH_CPP_LOG_LEVEL=INFO
export TORCH_DISTRIBUTED_DEBUG=DETAIL
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,COLL
```

```powershell
# PowerShell
$env:TORCH_CPP_LOG_LEVEL = "INFO"
$env:TORCH_DISTRIBUTED_DEBUG = "DETAIL"
$env:NCCL_DEBUG = "INFO"
$env:NCCL_DEBUG_SUBSYS = "INIT,COLL"
```

`TORCH_DISTRIBUTED_DEBUG` 的级别：

| 级别 | 用途 |
|---|---|
| `OFF` | 默认值，不增加额外检查。 |
| `INFO` | 输出 DDP 初始化信息，并改善未使用参数的报错信息。 |
| `DETAIL` | 额外检查集合通信的类型、顺序和张量 shape 是否在所有 rank 上一致，并输出运行时统计。 |

`DETAIL` 有额外同步与校验开销，仅建议在排错时开启。

若需要 C++ 调用栈，可额外设置：

```bash
export TORCH_SHOW_CPP_STACKTRACES=1
```

也可在程序中读取或调整调试等级：

```python
import torch.distributed as dist

print(dist.get_debug_level())
dist.set_debug_level_from_env()
```

## 2. 排查集合通信不一致

例如两个 rank 对 `all_reduce` 使用了不同 shape：

```python
tensor = torch.randn(10 if rank == 0 else 20, device="cuda")
dist.all_reduce(tensor)
```

未开启调试时，NCCL 可能挂起；设置 `TORCH_DISTRIBUTED_DEBUG=DETAIL` 后，PyTorch 会在执行底层通信前报告集合操作或 shape 不一致，而不是仅表现为超时。

所有 rank 必须以一致顺序调用集合通信：

```text
正确：rank 0 / rank 1 都执行 all_reduce → broadcast
错误：rank 0 执行 all_reduce → broadcast；rank 1 执行 broadcast → all_reduce
```

## 3. 使用 `monitored_barrier()` 定位失联 rank

普通 `dist.barrier()` 只能等待；某个 rank 未到达时，其他 rank 通常无法得知原因。

```python
from datetime import timedelta
import torch.distributed as dist

# 即使训练通信使用 NCCL，也可创建 Gloo 组进行主机端诊断。
group_gloo = dist.new_group(backend="gloo")

dist.monitored_barrier(
    group=group_gloo,
    timeout=timedelta(seconds=10),
)
```

若 rank 1 未能在 10 秒内到达，rank 0 会得到类似错误：

```text
RuntimeError: Rank 1 failed to pass monitoredBarrier in 10000 ms
```

这适合插在可疑代码的前后，确定哪一段代码导致某个 rank 停滞。

## 4. 使用 `dist.breakpoint()` 调试单个 rank

所有 rank 调用同一断点，但只有指定 rank 会进入交互式 `pdb`：

```python
# 每个 rank 都执行；只有 rank 0 连接终端调试器。
dist.breakpoint(rank=0)
```

其他 rank 会停在内部屏障中。当 rank 0 在 `pdb` 中输入 `c` 继续后，其他 rank 才会恢复。它适合检查局部变量、Tensor shape 和各分支的执行情况。

## 5. NCCL 网络与拓扑诊断

若自动选择的网卡错误，可显式指定：

```bash
export NCCL_SOCKET_IFNAME=eth0
export GLOO_SOCKET_IFNAME=eth0
```

集合通信卡住时：

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=COLL
```

怀疑 GPU、NVLink、PCIe 或网卡拓扑识别错误时：

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=GRAPH
```

所有节点应选择能够相互访问的网卡。Gloo 指定多张网卡时，所有进程必须配置相同数量的接口：

```bash
export GLOO_SOCKET_IFNAME=eth0,eth1
```

## 6. DDP 未使用参数

如果模型的某个参数未参与当前 iteration 的 loss，DDP 可能报错。`TORCH_DISTRIBUTED_DEBUG=INFO` 或 `DETAIL` 会在错误信息中给出未收到梯度的参数全名。

```python
ddp_model = torch.nn.parallel.DistributedDataParallel(
    model,
    device_ids=[local_rank],
    find_unused_parameters=True,
)
```

只有模型确实存在条件分支、部分参数在某些 iteration 不参与计算时才应启用 `find_unused_parameters=True`；它会增加额外开销。更根本的处理是让所有需要训练的参数参与 loss 的反向传播。

## 7. HTTP 调试服务器（实验性）

`torch.distributed.debug` 可启动跨 rank 的 HTTP 调试服务，收集堆栈、Flight Recorder 事件和性能数据：

```python
import torch.distributed.debug as dist_debug

dist_debug.start_debug_server(
    port=25999,
    dump_dir="./debug_dumps",
    dump_interval=60,
)

# 训练代码

dist_debug.stop_debug_server()
```

需要额外依赖：

```bash
pip install jinja2 aiohttp
```

该服务不面向公网安全设计，只能部署在可信网络中。

## 推荐排错顺序

```text
训练挂起或报错
  ↓
开启 TORCH_DISTRIBUTED_DEBUG=DETAIL、TORCH_CPP_LOG_LEVEL=INFO、NCCL_DEBUG=INFO
  ↓
检查日志中的 collective 类型、调用顺序、shape、网卡与 rank 信息
  ↓
在可疑位置前后加入 monitored_barrier()，定位未到达的 rank
  ↓
在问题 rank 使用 dist.breakpoint(rank) 检查局部状态
  ↓
长时间或复杂任务再使用 HTTP 调试服务器采集跨 rank 诊断信息
```
